Weft Developer Guide

Weft runs multi-agent coding workflows you write in TypeScript. Every step — an agent, a human, a shell command, an HTTP call — returns a schema-validated value; every run is journaled, resumable, and inspectable in a local web UI. One script runs on Claude Code (Agent SDK) or Codex (Codex SDK).

Install

npm i -g weft          # or: npx weft …
weft doctor            # checks node ≥ 24, git, provider credentials, .weft/ layout

Providers pick up the credentials you already have: the Claude adapter uses your Claude Code login or ANTHROPIC_API_KEY; the Codex adapter uses your Codex login or OPENAI_API_KEY.

Quickstart

weft new review                        # scaffolds .weft/workflows/review.ts (+ schemas.ts)
weft check review                      # tsc + gate
weft run review --base main --watch    # input fields become flags; --args '{…}' also works
weft ui                                # localhost: runs, live tree, report, answer requests

A complete first workflow — review the files changed since main, have Claude find bugs, have Codex try to refute each one, return only what survived:

// .weft/workflows/review.ts
import { defineWorkflow, z } from "@weft/sdk";
import { Finding } from "./schemas";                // relative imports are bundled and hashed with the script

export default defineWorkflow({               // name comes from the filename: "review"
  description: "Review changed files; keep only findings that survive refutation",
  input:  z.object({ base: z.string().default("main") }),
  output: z.object({ confirmed: z.array(Finding) }),
}, async (ctx, { base }) => {
  ctx.phase("Scope");
  const { files } = await ctx.git.changedSince(base);                         // [{ path, status }] · journaled
  const paths = files.filter(f => f.status !== "D").map(f => f.path);

  ctx.phase("Find");
  const found = ctx.ok(await ctx.parallel(paths.map(f =>
    ctx.agent(`Review ${f} for correctness bugs. Cite file:line and quote the evidence.`, {
      schema: z.object({ findings: z.array(Finding) }),                     // required on every step
      key: `review:${f}`,                                                 // stable identity for replay, tests, the tree
    }))));
  const findings = found.flatMap(r => r.findings);                          // typed — no nulls to filter

  ctx.phase("Verify");
  const confirmed = ctx.ok(await ctx.pipeline(findings)
    .step(f => ctx.agent(`Try to refute: ${f.claim} (${f.file}:${f.line}). Default real=false if unsure.`, {
      schema: z.object({ real: z.boolean(), reason: z.string() }),
      provider: "codex", key: `refute:${f.file}:${f.line}`,                // a different vendor grades
    }))
    .filter(verdict => verdict.real)                                        // drop refuted lanes
    .map((_verdict, f) => f)                                                // back to the finding
    .run());

  return { confirmed };
});

Anatomy of a workflow

  • defineWorkflow(meta, run) — meta has description and Zod input/output; name derives from the filename (override with name:). The engine validates both.
  • run(ctx, input) — plain async TypeScript. Everything comes through ctx; there are no ambient globals.
  • The graph is your code: await is a sequential edge, ctx.parallel fans out and joins, ctx.pipeline runs independent lanes, if on a typed field is a conditional edge, while is a bounded loop.
  • ctx.phase("Name") groups steps in the live tree; phases are discovered as the code runs.
  • Share schemas and helpers through relative imports (./schemas); they are bundled into the script and hashed with it. Files live in .weft/workflows/ and are callable by name; a session can also hand the engine an inline script.

Steps & failure

A step is anything that leaves the sandbox. Every step takes a schema (or has a fixed one) and returns a validated value — never prose, never null.

const plan = await ctx.agent("Plan the migration…", {
  schema: z.object({ steps: z.array(z.string()), risk: z.enum(["low", "medium", "high"]) }),
  key: "plan",                       // identity: replay, tests, explain. Optional; auto "Phase/agent#3" if omitted
  label: "migration plan",           // cosmetic, for the tree (defaults to key)
  provider: "claude",                // "claude" (default) | "codex"
  model: "claude-opus-5", effort: "high",
  maxTurns: 40, timeout: "10m",      // durations: "10m" | "2h" | number(ms) — everywhere in the API
});
if (plan.risk !== "low") { /* typed routing — the code takes the branch, not the model */ }

// when you need more than the value
const { value, usage, files, attempts, sessionId } = await ctx.agent.detailed("…", { schema: Plan });
if (usage.usd > 2) ctx.log("expensive plan");
  • Failure throws. ctx.agent throws a StepError (after schema repair and any retry) — it never resolves to null. Inside fan-out, failures are collected per branch (next section). onError: "null" exists for the rare case you want T | null.
  • Invalid output is repaired, not dropped: the engine re-prompts the same session with the validation errors (2 attempts by default). An agent that hits maxTurns gets one forced "finalize now" turn before the step fails — the expensive failure is avoided.
  • Any schema shape. schema: z.string() works — primitives are wrapped as { value } on the wire and unwrapped for you. Zod is the default; Valibot/ArkType work via Standard Schema.
  • Make decisions enums (verdict, severity, needs_human) and carry evidence with claims — the report renders it and integration checks it.
  • Tune retry: { attempts, backoff }, repair: 0, onMaxTurns: "fail" when you want different trade-offs.

Fan-out: parallel & pipeline

// independent branches: collect per-branch outcomes
const settled = await ctx.parallel(files.map(f => ctx.agent(`Review ${f}`, { schema: Review, key: `review:${f}` })));
// settled: Array<{ ok: true, value: Review } | { ok: false, error: StepError }>, input order
const reviews = ctx.ok(settled);                       // Review[] — failures logged + listed in the report
for (const s of settled) if (!s.ok) ctx.log(`skipped ${s.error.step.key}: ${s.error.message}`);

// one failure should abort everything: plain Promise.all — agent() throws
const [a, b] = await Promise.all([ctx.agent("…", { schema: A }), ctx.agent("…", { schema: B })]);

// lanes with stages; types flow stage to stage
const out = await ctx.pipeline(items)
  .step(item => ctx.agent(`…${item}`, { schema: Draft, key: `draft:${item.id}` }))   // (prev, item, i)
  .filter(draft => draft.confidence > 0.6)                                           // drops the lane
  .step((draft, item) => ctx.agent(`Verify…`, { schema: Verdict, key: `verify:${item.id}` }))
  .map((verdict, item) => ({ item, verdict }))
  .run({ concurrency: 4 });                                                         // Settled<{item, verdict}>[]
  • ctx.parallel accepts promises or thunks (() => ctx.agent(…)); scheduling is identical because the limiter lives inside every step. Results are in input order.
  • ctx.ok() is the only narrowing you need; it records what it dropped. Nothing is silently lost — the report lists every failed branch.
  • Stages in pipeline have no barrier between them; lane 3 can be on stage 2 while lane 1 is on stage 1. concurrency caps lanes per call; provider rate limits are configured per provider in engine config.

Humans & gates

// a gate: the run's approval policy decides — auto-approve and record, or ask a human
const go = await ctx.gate({ action: "Push fixes to origin/main", risk: "high", detail: summary });
if (!go.approved) return { pushed: false };

// always asks a person
const ok = await ctx.human.approve({ action: "Delete the legacy branch", detail });          // { approved, note? }
const pick = await ctx.human.ask({
  question: "Which module should we migrate first?",
  schema: z.object({ module: z.enum(["auth", "api", "billing"]), notes: z.string().optional() }),
  timeout: "2h", onTimeout: { default: { module: "auth" } },                // or "deny" | "escalate"
});
const fb = await ctx.human.review({ artifact: reportMd, schema: z.object({ verdict: z.enum(["ship", "revise"]), notes: z.string() }) });

A human step suspends the run durably. The process can exit; hours can pass; the answer arrives from the CLI (weft answer), the web UI, or the session that started the run — and weft resume continues from that exact line. Auto-approvals by policy are still recorded (answered_by: "policy").

Files, shell, network, secrets

Raw fs, fetch, child_process, and process.env are banned in workflow code. Use the journaled equivalents — they run in the engine, return structured values, and are served from the journal on replay:

const { paths } = await ctx.fs.glob("src/**/*.ts");
const { content, sha256 } = await ctx.fs.read("package.json");
const tests  = await ctx.exec("pnpm", ["test", "--reporter=json"], { schema: TestReport, timeout: "10m" });  // no shell, no quoting bugs
const top    = await ctx.bash("git log --oneline | head -5");                                       // when you need a pipe
const issues = await ctx.fetch("https://api.github.com/repos/o/r/issues?state=open", {
  headers: { Authorization: ctx.secret("GITHUB_TOKEN") },     // resolved engine-side at call time; journaled as <redacted>
  schema: z.array(Issue),
});
const region = await ctx.env.get("AWS_REGION");                 // journaled value; use ctx.secret for anything sensitive
await ctx.exec("git", ["push", "origin", "HEAD"], { risk: "high" });   // risk → gate → approval policy
  • exec/bash → { exitCode, stdout, stderr }; fetch → { status, headers, body } (non-2xx does not throw; check status). Pass schema to parse JSON stdout/body into a typed value.
  • Reading the same file twice is two steps — the second read after an agent edited it returns the new content. On replay you get what you observed then, never a fresh read.
  • Workflow code does not write files: edits are made by agents in worktrees (next sections) so they land as journaled patches. exec can of course write — do that deliberately.
  • fetch hosts are allow-listed in engine config; large outputs go to the blob store automatically.

Git utilities

ctx.git wraps the git CLI in typed, journaled steps so you don't parse porcelain output by hand. Reads cost nothing; writes carry a fixed risk tier that the run's approval policy turns into "auto" or "ask".

// reads — served from the journal on replay
const { branch, clean, staged, unstaged, untracked } = await ctx.git.status();
const { sha }      = await ctx.git.head();
const { files }    = await ctx.git.changedSince("main");                        // [{ path, status: "A"|"M"|"D"|"R" }]
const { patch, stats } = await ctx.git.diff({ from: "main", paths: ["src/**"] });   // from/to everywhere; to defaults to HEAD
const { commits }  = await ctx.git.log({ from: "main", max: 20 });                   // [{ sha, author, date, subject, body }]
const { lines }    = await ctx.git.blame("src/auth/login.ts", { lines: [40, 60] });
const { content }  = await ctx.git.fileAt("main", "package.json");
const { sha: base } = await ctx.git.mergeBase("main", "HEAD");

// writes — journaled, risk-tiered
await ctx.git.branch.create("fix/auth", { from: "main", checkout: true });   // low → auto
await ctx.git.commit({ message: "fix(auth): bound the loop", paths: ["src/auth/**"] });   // low → auto, returns { sha }
await ctx.git.pull({ rebase: true });                                    // medium → ask
await ctx.git.push({ branch: "fix/auth", setUpstream: true });           // high → ask (or auto for allow-listed remotes/branches)
await ctx.git.reset({ to: base, mode: "hard" });                         // irreversible → ask + typed confirm
TierOpsDefault
readstatus · head · branches · mergeBase · changedSince · diff · log · show · blame · fileAt · snapshotno approval
lowadd · commit · branch.create · checkout · fetch · stash.push / pop · tagauto, recorded
mediumpull · reset (soft/mixed) · apply · stash.drop · checkout --discardask
highpushask
irreversiblepush --force · reset --hard · branch.delete · clean · remote tag deleteask + typed confirm
  • A workflow can raise a tier ({ risk: "high" }), never lower it. Relax what "ask" means in engine config, with patterns: approvalPolicy: { push: { "origin/main": "ask", "origin/wip/*": "auto" } }.
  • cwd defaults to the run's integration tree; inside a write step's agent it is that step's worktree.
  • Large patches go to the blob store; diff returns a ref plus stats so you can decide before reading it.
  • On resume, a journaled write is served if its sha/ref still exists; otherwise it re-runs and the run is marked diverged — weft replay --dry tells you beforehand.

Write steps & merging

const fixes = ctx.ok(await ctx.parallel(bugs.map(b =>
  ctx.agent.detailed(`Fix this bug and add a focused test: ${b.claim}`, {
    schema: z.object({ summary: z.string(), tests: z.array(z.string()) }),
    isolation: "worktree",                                              // own git worktree at the integration tree
    write: { paths: [b.file, "**/*.test.ts"], also: ["pnpm-lock.yaml"], mode: "warn" },   // scope is told to the agent verbatim
    key: `fix:${b.file}`,
  }))));
await ctx.integrate(fixes, { order: "sequential", onConflict: "ask" });   // explicit: these patches, this order
await ctx.check("tests", { exec: ["pnpm", "test"], required: true });           // pass | fail | trust-prior | skipped
  • A write step returns a patch (on .detailed() results), not a mutated tree. ctx.integrate(patches) merges exactly what you pass, in that order, as journaled steps — so weft resume on a fresh clone rebuilds the tree from the journal. A run that ends with un-integrated patches fails unless you ctx.discard() them.
  • Scopes default to mode: "warn": out-of-scope edits are flagged in the report and the patch still lands. mode: "strict" quarantines the patch instead — use it when two writers really must not touch the same files. Either way the agent is given its scope explicitly in its prompt.
  • On Claude the scope is enforced live (edit tools outside it are denied); on Codex it is checked after the run. Steps without write are read-only: on Claude every edit tool is denied for them.
  • trust-prior: ctx.check("tests", { trustPrior: { run: "7f3a", reason: "unchanged since" } }) records a deliberately skipped re-run.

Sub-workflows, budget, routing

import fixPass from "./fix-pass";
const result = await ctx.workflow(fixPass, { plan }, { budget: { fraction: 0.3 } });   // typed by fixPass's input/output
const other  = await ctx.workflow("fix-pass", { plan });                              // by registry name — returns unknown; prefer the import
ctx.log(`spent $${ctx.budget.spent.usd} / ${ctx.budget.remaining.tokens ?? "∞"} tokens left`);
  • A child run has its own journal and is resumable on its own; the parent step's result is the child's validated output. Budget, concurrency, abort, and agent caps are inherited. Depth ≤ 3.
  • Set a run budget with --budget 500k (tokens) or --budget $5. Exhaustion throws inside the next step; ctx.budget.{spent,remaining}.{tokens,usd} are exact, from provider usage.
  • Routing resolves step opts → workflow defaults → engine config. Defaults: claude-opus-5 at effort high. Use claude-sonnet-5 / low deliberately for mechanical stages. Per-provider rate limits live in engine config.

Rules the gate enforces

weft check (and every run) parses your script first:

Don'tDoWhy
Date.now(), new Date(), Math.random()ctx.now(), ctx.random(), ctx.uuid()journaled, so replay is deterministic
import fs, global fetch, child_process, timers, process.envctx.fs.*, ctx.fetch, ctx.exec/bash, ctx.sleep, ctx.env/secretside effects become resumable steps; secrets stay out of the journal
bare package imports (other than @weft/sdk + allow-list)relative imports; put helpers in ./libthe bundle is hashed; node builtins and network libs would escape the sandbox

Missing schema is a TypeScript error, not a runtime one — weft check catches it.

Running, resuming, inspecting

CommandWhat it does
weft run <name|file|-> [--<input> v | --args json] [--budget …] [--watch]start a run; input fields become flags; - reads an inline script from stdin
weft ls · weft status <run>list runs / one run's tree, pending requests, cost
weft answer <run> [<req>] [json]answer a human request — with no JSON it renders the request's schema as interactive prompts
weft resume <run> [--reuse content|key]replay and continue, also after editing the script. content (default): a step is reused only if its prompt/opts are unchanged. key: reuse by identity even if you reworded the prompt — fast iteration, deliberate staleness
weft replay --dry <run> [--reuse …]replay without calling providers; prints hits / salvaged / diverged
weft uilocal web UI (one daemon per machine on localhost:4781; registers this repo's .weft/runs): runs, live tree, explain, output diff, report, answer
weft explain <run> [key|seq] · weft report <run> · weft diff <a> <b>step prompt/output/usage/transcript · generated report · structured diff of step outputs
weft cancel <run>abort in-flight agents; the run stays resumable
 
.weft/runs/<id>/
  journal.jsonl     # the truth — every step, request, answer, patch (secrets redacted)
  script.ts         # what ran, bundled (+ source map, so errors point at your .ts lines)
  blobs/            # patches, transcripts, big outputs
  state.json        # projection: status, steps, scopes, checks
  report.md         # projection: outcome, changes, checks, ledger, remaining risk

What resume reuses, honestly. Default replay reuses a step only if its inputs are byte-identical — so rewording a prompt re-runs that step and everything downstream that embedded its output. Reordering or inserting steps is fine. When you are iterating on wording, --reuse key keeps yesterday's answers for steps whose key still exists; replay --dry shows the plan before any model is called.

From Claude Code or Codex

Register the MCP server once; then ask the session in plain language.

// Claude Code — .mcp.json
{ "mcpServers": { "weft": { "command": "npx", "args": ["-y", "@weft/mcp"] } } }

# Codex — ~/.codex/config.toml
[mcp_servers.weft]
command = "npx"
args = ["-y", "@weft/mcp"]
> Use weft to run the review workflow against main and show me only confirmed findings.
  1. weft.run returns { runId } immediately (a workflow name or an inline TypeScript script; weft.types returns the ctx typings if the session wants to write one).
  2. weft.wait(runId, { timeout: "10m" }) long-polls and returns on the next status change: the typed output, or { awaiting: { id, kind, question, schema } }.
  3. On awaiting, the session asks you with its own question tool, calls weft.answer, and waits again. It never parses prose. Works identically in Claude Code and Codex.

Testing workflows

import { runWorkflow, mock } from "@weft/testing";
import review from "../.weft/workflows/review";

test("keeps only findings that survive refutation", async () => {
  const { output, journal } = await runWorkflow(review, {
    input: { base: "main" },
    provider: mock()
      .on({ key: "review:*" }, () => ({ findings: [{ file: "a.ts", line: 3, claim: "off-by-one", evidence: "for (i <= n)" }] }))
      .on({ key: "refute:*" }, (req) => ({ real: req.prompt.includes("off-by-one"), reason: "loop bound" })),
    git: { changedSince: { files: [{ path: "a.ts", status: "M" }] } },
  });
  expect(output.confirmed).toHaveLength(1);
  expect(journal.steps({ kind: "agent" })).toHaveLength(2);
  expect(journal.step("refute:a.ts:3").prompt).toContain("Default real=false");
});

Fixtures match on key (globs), get the real request (prompt, opts), and are validated against the step's schema — a fixture that wouldn't pass in production fails the test. journal.toMatchSnapshot() catches accidental graph changes.

StepError: refute:a.ts:3 — schema repair exhausted (2 attempts)The agent couldn't produce valid output. Simplify the schema (flat, enums) or tighten the prompt; attempts are in weft explain <run> refute:a.ts:3.
